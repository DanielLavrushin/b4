API and MCP tools

The web interface works through a REST API that b4 serves on the web server's port, under /api/. The API reference on this site lists every endpoint with its parameters and responses. With the address of a running b4 in its B4 Instance field, that page sends its requests to that instance; without one, it only shows the reference.

Authentication​

While a username and a password are set under Settings > System > Web Server, every request under /api/ needs a login token, except those to /api/auth/ and /api/version. Without a username and password, no token is needed.

StepRequest
Log inPOST /api/auth/login with {"username": "...", "password": "..."} returns {"token": "..."}
Use the tokenAn Authorization: Bearer <token> header on every request. WebSocket connections under /api/ws/ can pass it as the token query parameter instead
Log outPOST /api/auth/logout revokes the token

A login token stays valid while it is used at least once every 24 hours, and is discarded when b4 restarts. After repeated failed logins from one address, b4 answers 429 for a while. The MCP endpoint has a token of its own, see MCP server.

Watchdog reason codes​

The watchdog reports why a set is in its state, or how its last heal ended, as one of these codes. The Watchdog page shows the same reasons in words.

CodeMeaning
not_ownedThe set's addresses are handled by another set or by none, so a strategy written into this set does not affect them
escalatedAn escalation sends the addresses to another set
unusableA certificate error, a required client certificate, or a private or local destination. Never healed
current_worksTested alone, the set's own strategy loads the addresses, yet the live check fails
not_neededTested alone, the addresses load without a bypass, yet the live check fails
partialThe search found a strategy for only some of the addresses, so nothing was written
noneThe search found no working strategy
incompleteThe search ended without a confirmed result
budgetThe search ran longer than 20 minutes and was canceled
start_failedThe Discovery run could not start
verify_failedThe strategy written did not pass the live check and was undone
editedThe set was changed during the check or the search, so nothing was written
busyAnother Discovery run holds the runtime, and the heal waits
rules_changedb4 was applying or rewriting the firewall rules the search depends on, such as its DSCP rules, so nothing was written; the heal is tried again later

Exposure reasons​

For an Expose to internet switch that is on but opened nothing, GET /api/system/addresses gives the reason as one of no_auth, web_no_auth, open_relay, shared_port, loopback, invalid_bind and not_listening. Securing the web interface describes the conditions of each switch.

MCP server​

POST /api/mcp serves the Model Context Protocol to AI applications, as JSON-RPC 2.0 over HTTP. Connecting an AI assistant covers the setup. Only POST is served: GET and DELETE return 405, which is normal for this transport.

SituationResponse
Enable MCP server is off404, mcp server is disabled
An MCP token is set, and the request carries none or another one401, invalid or missing MCP token
No MCP token is setThe web interface's login token is required, as for the rest of the API, while a username and password are set
The request carries an Origin header that is not allowed403

A request with an Origin header is accepted when that origin is b4's own address written as an IP address or localhost, or is listed in system.web_server.mcp.allowed_origins, where a single * accepts any origin. A host name is never accepted automatically: under DNS rebinding, a page on an attacker's name reaches b4 with matching Origin and Host headers. AI applications send no Origin header.

Tools​

The server offers tools according to the two permission switches on the MCP server card and rebuilds the list when they change, without a restart. An application that was connected before the change keeps its old list until it reconnects. A tool that is not permitted is not offered at all, and the server tells the model which permission is off, so the model can say what to turn on.

PermittedTools offered
Nothing (default)14
Allow configuration changes18
Allow active probes16
Both20

b4_check_domain answers whether a domain is configured in a set. b4_recent_connections answers whether traffic for it arrived and which set matched. The difference separates a targeting mistake from a routing one.

A ready-made prompt, diagnose_domain, comes with the tools. It takes a domain and walks the model through the status, the coverage, the configuration and the firewall rules, in that order. Applications that support prompts list it separately.

Reading the watchdog's verdicts emits no traffic and changes nothing, so the tool is offered at every level, and each action is permitted on its own. Without set, the actions work on the older per-domain list and the global watchdog switch:

b4_find_bypass_strategy​

domains takes up to five domains or full URLs, separated by commas, as the Discovery input does: a domain is fetched as https://<domain>/, a URL as given. A host that only serves files, such as an image or video CDN, can answer / with HTTP 400 and leave the run nothing to test. Such a host is probed by the URL of a file it serves. A run also tries the strategies the community hub publishes for the domains, as a run from the Discovery page does when the hub is on.

action=start with set runs Discovery for that set: on the domains given, or on the set's Discovery addresses, at most five. The set's current strategy is tested first, and the search stops at the first strategy confirmed on every address. action=status reports the verdict, and action=apply with set writes the result into the set, the strategy only and only for the verdict covered. The same applies to action=apply without set when the run it refers to was a run for a set. A set that action=apply creates for free-form domains keeps the addresses they were found on as its Discovery addresses. A set with routing enabled is refused, and so is a result whose probes took another DSCP path than the set's traffic takes now, as on the Discovery page.

Changing settings​

With Allow configuration changes on, these become writable:

  • every setting inside a set: targets, fragmentation, faking, TCP and UDP, DNS, escalation and routing;
  • the MTProto and SOCKS5 settings, the Telegram over WebSocket switch system.mtproto.bridge.enabled among them;
  • the logging settings, so the model can raise the log level, reproduce a problem and read the result.

b4_list_writable_paths reports the exact paths with their types, current values and accepted values. A change goes through the same validation and live-apply path as a save in the web interface. An invalid result is rejected and nothing is saved, and an accepted one applies at once, firewall rules included. Writing a list, such as a set's domains, replaces the whole list, so a model reads the current value first and sends it back in full.

b4_edit_set_targets adds and removes single entries instead, with kind naming the list: sni_domains, ip, geosite_categories, geoip_categories, asns or source_devices. An asns entry is written as AS15169 or 15169 and stored as the bare number; reserved numbers are refused. An ASN whose prefixes b4 has not fetched yet is added anyway and fetched at once, and the reply names it, because until the fetch succeeds the set matches none of its addresses.

Whatever the switches say, the credentials of the web interface, SOCKS5, MTProto and a set's upstream proxy are refused, and so are these:

RefusedReason
Web server settingsMoving or locking the interface removes the way to undo the change
The MCP settingsThe model cannot widen its own permissions
Capture engine and TUNSwitching it under a live network can cut the machine off
Firewall backendA wrong value leaves the machine with no rules at all
Every Expose to internet switch, and any write that would open a port while one of them is on, such as turning the MTProto proxy on or changing its portAn open port is reachable from the whole internet at once, and a revert does not undo what reached it
Packet marks and routing tablesb4's own traffic depends on them
Set DSCP (system.tables.dscp) and a set's own DSCP (sets[].dscp)Rules on the next router act on the value, and a wrong one can send traffic down another route

The dividing line is recoverability: a wrong value inside a set breaks some sites, visibly and reversibly, while a wrong web server port or capture engine can leave the machine unreachable. The writable areas are named as whole subtrees, and the exclusions are marked on the fields themselves, so a setting added to b4 later stays unwritable until it is opted in. Refusing a location does not refuse the contents: b4_logs_tail reads both log files wherever the directory points.

b4_revert_last_change restores the configuration from before the most recent change made over MCP since b4 started, and applies it. Repeating it walks further back. It is refused, and the change stays on the list, when the configuration changed after that change, by a watchdog heal, the web interface or another tool. It is also refused when it would switch a set's watchdog or the global watchdog on, or bring back watched domains or the Discovery addresses of a watched set, while Allow active probes is off.

Topics​

Several b4 settings have names that read as something other than what they do, and a zero usually means "use the fixed value" rather than "off". b4 carries a written description of such settings, and the server tells the model to read it before explaining or changing anything. The descriptions come from src/ai/topics.json, built into the binary; the web interface's AI explanations use the same text.

The descriptions are published twice:

  • the tool b4_get_topic, with topic for an exact key, path for the setting a b4_set_config_value path names (in sets[video].tcp.win.mode the set is ignored), or query for a search. With no arguments it lists every documented key;
  • the resources b4://topics/<key>, with the same text.

Most applications never show resources to the model; LM Studio and the OpenAI-compatible bridges list them for the user. The tool makes the text reachable for the model. A question about a setting without a description returns a note saying so, with the documented settings nearby. The note tells the model to say it is unsure rather than guess the setting's unit, default or meaning from its name.

b4_api_reference​

The tool gives the model the reference that the API reference page shows, from a copy built into b4 that matches the installed version. It covers what the other tools leave out, and the model makes the API calls itself. The tool only describes the API.

ArgumentsAnswer
NoneEvery operation, by tag
queryThe operations whose path, summary or description contain every word given
operation, as PUT /api/sets/{id}The operation's parameters, request body and responses, with the types they use. A path with a real value, such as /api/sets/abc123, names the same operation
schemaOne type from an earlier answer, with its fields

A type too large for one answer is listed by name, for a later call with schema. An operation that another tool also performs names that tool. A REST write passes b4's own validation, but not the checks and refusals that the MCP tools add.

Apart from schema, each answer also explains how to call the API. While a username and a password are set, that is the login, and the model is told to ask the user before using them. The MCP token is refused outside /api/mcp.

What b4 records​

Every tool call writes one line to b4's log, shown on the Logs page: the tool, the caller's address and how long it took. A refused call is logged as a warning. A request turned away at the endpoint is logged too: the server off, a wrong or missing token, or a browser origin that is not allowed. The token itself is never written. Repeated refusals are collapsed into one line every 30 seconds, with a count. These lines go to the live log and the console, not to errors.log, which holds errors only.

A change made or reverted over MCP also appears under Recent changes on the dashboard as AI agent changed a setting, with the path of the setting and without its value.

What is stripped​

Tool output may be forwarded to a third-party model, so b4 removes these values from it or replaces them with [redacted]:

  • the username and password of the web interface;
  • the MCP token;
  • the SOCKS5 username and password;
  • the names and values of the MTProto secrets;
  • the IPinfo token;
  • the reference to the stored AI API key;
  • the username and password of a set's upstream proxy;
  • the path of the web server's TLS key.

Host names and URLs are returned as configured. Download safe copy under Settings > System > Backup masks those as well. b4_diagnostics holds no credentials, but it reports the hostname, every interface address and the live firewall ruleset, which is enough to identify the network.
