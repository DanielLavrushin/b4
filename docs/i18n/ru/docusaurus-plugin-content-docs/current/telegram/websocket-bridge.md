# Telegram через WebSocket

Режим маршрутизации сета. Когда устройство за b4 открывает соединение к дата-центру Telegram, b4 перехватывает его, разбирает сессию и ретранслирует её через WebSocket-узел Telegram, а за ним идут маршруты через Cloudflare. В самом Telegram на устройстве ничего не настраивается, VPS не участвует.

Режим работает сам по себе. MTProto-прокси в разделе Настройки, MTProto включать не обязательно: мост создаётся при старте в любом случае.

## Требования

Мост работает через TPROXY, которому нужны модули ядра `tproxy` и `socket`. Без них b4 пишет в лог, что прозрачное перенаправление недоступно, и режим молча ничего не перенаправляет. В OpenWrt это пакеты `kmod-nft-tproxy` и `kmod-nft-socket`; то же требование описано в разделе [Маршрутизация](../sets/routing.md).

Для сопоставления Telegram по гео-категориям нужны настроенные базы GeoSite и GeoIP. Сет, в котором указана категория, а путь к соответствующей базе пуст, отклоняется при сохранении конфигурации.

## Настройка

1. Создать сет и указать ему **GeoIP**-категорию `telegram`. Правило перехвата сопоставляет адреса, поэтому направляет трафик именно GeoIP-часть. Категория GeoSite `telegram` добавляет адреса, полученные из DNS-ответов, которые видит b4, и для устройства, резолвящего через DoH или DoT, не даёт ничего.
2. На вкладке сета **DNS & Маршрутизация** включить маршрутизацию и выбрать **Режим маршрутизации** *Telegram через WebSocket (встроенный)*.
3. Выбрать **Исходные интерфейсы**, устройства которых должны идти через мост, либо оставить список пустым.

```json
{
  "name": "telegram-ws",
  "targets": {
    "geosite_categories": ["telegram"],
    "geoip_categories": ["telegram"]
  },
  "enabled": true,
  "routing": { "enabled": true, "mode": "mtproto-ws" }
}
```

:::warning Ограничение по источникам делает больше, чем кажется
Правила, отправляющие в мост собственный трафик роутера, устанавливаются только пока сет не ограничен исходными интерфейсами или устройствами. Выбор исходного интерфейса исключает из моста и сам роутер, а не только устройства на других интерфейсах.
:::

## Что мост берёт из настроек транспорта

Общие настройки [транспорта к Telegram](./upstream.md) действуют, но с двумя подменами, которые мост делает для каждой сессии:

- Режим транспорта принудительно ставится в **Авто**, что бы ни было выбрано в списке.
- **DC Relay** очищается. Релей, настроенный для прокси-сервера, здесь не используется, поэтому сеть, где заблокирован WebSocket-транспорт, в этом режиме релеем не спасается.

Мост также не держит прогретого пула WebSocket-соединений, только пул Worker-ов, поэтому каждая сессия набирает соединение с Telegram «на холодную» в том же бюджете времени, для которого у прокси-сервера есть прогретые запасные. Первое соединение через мост поднимается заметно дольше, чем такое же через прокси-сервер.

Если не загружаются медиа, стоит указать [домен Cloudflare Worker](./cloudflare-worker.md): дата-центры, которые не обслуживает собственный узел Telegram, доступны только через маршруты Cloudflare.

## Границы

Через мост идут только TCP-сессии MTProto.

- Соединение, которое b4 не может разобрать или сопоставить с дата-центром, сначала предлагается настроенному Cloudflare Worker и только потом набирается напрямую.
- Голосовые звонки не перехватываются вовсе. Для сета в этом режиме обработка UDP отключается и слушающий UDP-сокет не создаётся, поэтому звонки идут обычным путём.
- Правило отклонения QUIC не устанавливается, поэтому клиент, предпочитающий QUIC, обходит мост без единой строки в логе.
- У правила перехвата нет фильтра по порту назначения. В слушающий сокет моста попадает любое TCP-соединение к совпавшему адресу Telegram, включая обычный HTTPS к `web.telegram.org` или `t.me`: такое соединение читается, опознаётся как не-MTProto и ретранслируется дальше.

:::info Обход DPI для такого сета выключен
У сета, направленного через TPROXY, обработка пакетов отключается: совпавшие пакеты пропускаются без изменений, поэтому faking, фрагментация и десинхронизация к ним не применяются. Мост заменяет обход, а не дополняет его.
:::

Соединение, дошедшее до слушающего сокета и не приславшее ни байта, занимает его на время **Ожидания рукопожатия в мосте**, по умолчанию 180 секунд. Значение `-1` означает ожидание без ограничения, а не отключение ожидания.
