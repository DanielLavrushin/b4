# Движок захвата

У b4 есть два способа забрать пакет из ядра и передать его собственному коду. Какой из них работает, определяет `queue.mode` в разделе **Настройки → Основные → Движок пакетов → Режим захвата**. Значение читается один раз при старте, поэтому изменение вступает в силу только после перезапуска сервиса.

| Движок | `queue.mode` | Как пакеты попадают в b4 |
| --- | --- | --- |
| NFQUEUE | `nfqueue` (по умолчанию, хранится как пустое значение) | Правила iptables или nftables кладут подходящие пакеты в очередь netfilter; b4 читает каждый и возвращает вердикт |
| TUN | `tun` | Policy routing заводит подходящие пакеты в виртуальный интерфейс, которым владеет b4; b4 читает их оттуда и переотправляет принятое через raw-сокет |

Всё, что находится выше уровня захвата, в обоих режимах одно и то же: сеты, цели, стратегии, обработка DNS и маршрутизация читают те же пакеты и принимают те же решения. Различается только то, какие пакеты доходят, и об этом раздел [Ограничения](#ограничения).

## Зачем нужен TUN

Движку NFQUEUE нужны `nfnetlink_queue` и цель `NFQUEUE` в ядре. В нескольких стоковых прошивках роутеров нет ни того, ни другого, и пакета, который бы это добавил, тоже нет - в таком случае b4 вообще не видит трафик. `/dev/net/tun` присутствует в куда большем числе таких прошивок, потому что он нужен собственному VPN-клиенту вендора, поэтому TUN работает на железе, где NFQUEUE запустить нельзя.

Второй случай - роутер, у которого WAN поднят через L2TP или PPP и периодически пересоздаётся: движок TUN следует за системным маршрутом по умолчанию и сам переключает аплинк, когда этот маршрут меняется.

:::info
TUN - это запасной вариант, а не улучшенный. У него есть перечисленные ниже ограничения, а NFQUEUE - это режим, который описывают все остальные страницы сайта. Менять настройку имеет смысл только тогда, когда NFQUEUE на этом железе не работает.
:::

## Требования

| Требование | Зачем |
| --- | --- |
| `/dev/net/tun` | Движок открывает символьное устройство, чтобы создать свой интерфейс. Без него b4 в режиме TUN не стартует |
| Бинарник `iptables` или прослойка совместимости `iptables-nft` | Все правила движка пишутся через `iptables`: SNAT в устройство, разрешения в `FORWARD`, правила `NOTRACK` для переотправленных пакетов и сама цепочка захвата. Нативных правил nftables для TUN нет, поэтому система только с `nft` получает отказ при старте с указанием причины |
| Policy routing из полноценного iproute2 | Движок добавляет записи `ip rule` по меткам файрвола и кладёт маршруты по умолчанию в таблицы 9999 и 9998. Апплет `ip` из busybox часто не принимает произвольный id таблицы, и тогда `ip rule add` завершается ошибкой с упоминанием iproute2 |

Запуск b4 с `--skip-tables` снимает требование к `iptables`: движок тогда создаёт только устройство, маршрутизацию захвата и таблицу обхода, а NAT и форвардинг для TUN-устройства нужно настроить самостоятельно.

Метка очереди проверяется на пересечение с битами, которые движок резервирует за собой: `0x40000000` для перенаправления, `0x20000000` для клиентского направления и `0x10000000` для переотправки. `queue.mark`, пересекающаяся с любым из них, отклоняется при сохранении конфигурации.

## Два режима захвата

При старте движок проверяет, принимает ли `iptables` правило с `connbytes`, и выбирает один из двух способов завести трафик в устройство.

| Режим | Когда выбирается | Что захватывается |
| --- | --- | --- |
| `ports` | `xt_connbytes` доступен | Только первые пакеты соединения на TCP- и UDP-портах, перечисленных включёнными сетами, плюс каждый UDP-запрос на порт 53. Количество берётся из глобальных лимитов пакетов, по умолчанию `19` для TCP и `8` для UDP. Системный маршрут по умолчанию не трогается |
| `default` | `xt_connbytes` отсутствует | Системный маршрут по умолчанию заменяется маршрутом в TUN-устройство, поэтому через b4 проходит всё, что роутер отправляет в интернет |

В режиме `ports` перенаправлением занимается цепочка `B4_TUN` в таблице mangle, вызываемая из `PREROUTING` и `OUTPUT`. Она метит описанные выше пакеты, а правило policy routing отправляет эту метку в таблицу, где маршрут по умолчанию ведёт в TUN-устройство. Всё остальное идёт обычным путём, а трафик, который уже забрал маршрутизирующий сет, выходит из цепочки нетронутым.

В режиме `default` цепочки нет: маршрут по умолчанию в основной таблице указывает на устройство, а принятые пакеты переотправляются с меткой, которую второе правило policy routing отправляет в таблицу обхода с настоящим маршрутом до аплинка.

Режим `default` захватывает больше и обходится дороже. Каждое пересылаемое соединение читается целиком, пока оно живо, а не только на первых нескольких пакетах.

### Какой режим активен

Активный режим сообщается в трёх местах.

- Лог при старте. Режим `ports` пишет `TUN: port-capture mode - first N tcp / M udp packets on ports ...`; режим `default` - `TUN: xt_connbytes not available; capturing the whole default route ...`, а следом `TUN: default-capture routing configured ...`. Периодическая строка heartbeat повторяет это, называя устройство, аплинк, режим и счётчики.
- **Настройки → Информация о системе**, раздел **Движок**, поле **Захват**.
- Сама цепочка:

```sh
iptables -t mangle -S B4_TUN
```

Заполненная цепочка означает режим `ports`. Ответ `No chain/target/match by that name` означает режим `default`, в котором такая цепочка не создаётся.

## Настройки, действующие только в режиме TUN

Раздел `queue.tun` в файле конфигурации. Четыре поля из шести имеют элемент управления в **Настройки → Основные → Настройки TUN**, который появляется при выборе режима захвата TUN; остальные два задаются только в файле.

| Поле | Интерфейс | По умолчанию | Значение |
| --- | --- | --- | --- |
| `device_name` | Имя устройства TUN | `b4tun0` | Имя интерфейса, который создаёт b4. Существующий интерфейс с таким именем удаляется, если это TUN-устройство от предыдущего запуска, и вызывает отказ, если это что-то другое |
| `address` | Адрес TUN | `10.255.0.1/30` | Адрес и префикс на устройстве. Пересечение с подсетью LAN или VPN ломает маршрутизацию для этой подсети |
| `address_v6` | - | пусто | IPv6-адрес устройства. IPv6 в режиме TUN не пересылается, поэтому заполнение поля только оставляет IPv6 включённым на интерфейсе и добавляет предупреждение в лог |
| `out_interface` | Аплинк-интерфейс | пусто | Куда уходят обработанные пакеты. Пусто или `auto` - следовать системному маршруту по умолчанию и переключаться при его смене; указанный интерфейс закрепляется |
| `out_gateway` | Шлюз аплинка | пусто | Шлюз для закреплённого аплинка. Пустое значение берётся из текущего маршрута по умолчанию. Поле заблокировано, пока аплинк в режиме «Авто» |
| `route_table` | - | `9999` | Id таблицы маршрутов для обхода. Маршрут захвата ложится в `route_table - 1`, то есть по умолчанию это пара 9999 и 9998. Таблица, где уже есть маршруты не от b4, вызывает отказ с указанием выбрать свободный id |

Имя устройства, адреса и таблица маршрутов читаются только при старте. Их изменение на работающем сервисе пишет предупреждение и требует перезапуска.

:::note Что интерфейс скрывает в режиме TUN
Выбор движка файрвола, интервал мониторинга правил, переключатель **Пропустить настройку IPTables/NFTables** и фильтр **Сетевые интерфейсы** скрыты, пока выбран режим захвата TUN, потому что ни одно из этого не применяется: движок работает с `iptables` напрямую, поддерживает свои правила по собственному расписанию и не имеет фильтра захвата по интерфейсам. NAT masquerade остаётся, он описан в разделе [Основные](./core#фаервол).
:::

## Ограничения

По состоянию на 1.80.0 в режиме TUN верно следующее. Диагностический отчёт перечисляет те из них, которые относятся к текущей конфигурации, в поле `engine.limitations`.

### Дискавери недоступен

Дискавери гоняет свои пробы через вторую очередь netfilter, со своими номерами очередей, своими метками и своими правилами перенаправления. Эквивалента этому в движке TUN нет, поэтому запуск дискавери в режиме TUN отклоняется с указанием причины, а не возвращает результат, который ничего не описывает. Это касается запуска со страницы [Дискавери](../discovery.md), запуска из мониторинга доменов и инструмента MCP.

[Мониторинг доменов](../watchdog.md) опирается на дискавери в своём самовосстановлении: когда домен падает достаточно часто, он перезапускает дискавери и применяет результат. В режиме TUN он этого сделать не может и помечает такой домен как невосстановимый, с одним предупреждением в логе. Проверки доступности продолжают работать, поэтому мониторинг по-прежнему показывает, какие домены не отвечают; прекращается только автоматический ремонт. Стратегия, выбранная вручную, применяется обычным образом.

### IPv6 не пересылается

Движок читает IPv4 и отбрасывает IPv6. Дошедший до устройства IPv6-пакет учитывается и отбрасывается, с одним предупреждением при первом случае, а счётчик виден в **Информации о системе** как **Отброшено IPv6**.

Включение **поддержки IPv6** этого не меняет. b4 предупреждает всякий раз, когда у хоста есть рабочий глобальный IPv6-адрес, а работает движок TUN: dual-stack сайт, на который нацелен сет, в этом случае открывается по IPv6 и обходит сет целиком. Остаётся выключить IPv6 на WAN или переключить движок на NFQUEUE. [Откат на IPv4](../dns#откат-на-ipv4) продолжает работать для ответов, которые b4 видит, и сужает разрыв, не закрывая его.

### DNS к собственному резолверу роутера не перехватывается

Ядро смотрит в таблицу `local` раньше любых правил policy routing от b4, поэтому запрос, отправленный клиентом на собственный адрес роутера на порт 53, попадает к работающему там резолверу - на большинстве прошивок это dnsmasq - до того, как правило захвата успеет его перенаправить. Резолвер сета, его закрепления и его блокировки к таким запросам не применяются.

То, что роутер затем отправляет наверх, уходит через `OUTPUT`, где правило захвата уже действует, поэтому сет всё-таки видит запрос и может на него ответить. На практике это означает, что к запросу не привязан адрес клиента, а запрос, на который локальный резолвер ответил из своего кеша, до b4 не доходит вовсе. Что делает перехват там, где он применяется, описано в разделе [DNS](../dns.md).

### У захвата всего маршрута по умолчанию нет цепочки захвата

В режиме `default` перенаправление сделано маршрутом, а не правилом, поэтому несколько возможностей, живущих в цепочке `B4_TUN`, отсутствуют:

- Фильтрация по устройствам. Списки разрешённых и запрещённых - это правила `mac-source` в цепочке `B4_TUN_GATE`, которая создаётся только в режиме `ports`.
- Захват обратного направления, описанный ниже.
- Ранние возвраты, которые выводят адреса маршрутизирующего сета из пути захвата. Защита по метке всё равно не пускает маршрутизируемый трафик в устройство, ценой нескольких лишних проверок правил.
- Ограничение на первые N пакетов. Каждое соединение читается всю свою жизнь, и это основная цена этого режима.

### Данные TCP в обратном направлении не захватываются

Правила захвата метят исходящее направление. Единственное исключение - пакеты TCP RST на портах, перечисленных сетами: они метятся, только пока у включённого сета задействованы RST-защита или эскалация, и только в режиме `ports`.

Поэтому всё, что b4 делает с входящими данными TCP, не работает: режимы [обхода входящих ответов](../sets/tcp/faking#обход-входящих-ответов-incoming), которые действуют на ответ сервера после порога переданных данных, и сигналы доступности, которые b4 снимает с SYN-ACK от сервера и которые питают детектор блокировки IP и список известных рабочих адресов. Сеты продолжают работать на исходящем направлении, где и действуют стратегии обхода DPI.

У захвата обратного направления отправитель создаётся при старте, поэтому включение RST-защиты или эскалации в сете требует перезапуска.

### Egress IP сета не сохраняется для захваченного трафика

Трафик на пути в TUN-устройство проходит SNAT на собственный адрес аплинка, чтобы ответы возвращались, и b4 читает пакет уже после этой замены. Переотправленный пакет несёт `NOTRACK`, поэтому ни одно последующее правило NAT его тоже не видит.

Маршрутизирующий сет обычно на этот путь не попадает: и цепочка захвата, и цепочка SNAT делают ранний возврат для пакета, который сет уже пометил, поэтому сет, маршрутизирующий на выходной интерфейс, сохраняет свой адрес источника, и его [egress IP](../sets/routing#egress-ip) действует. При захвате всего маршрута по умолчанию цепочки захвата нет, и на переотправляемый там трафик egress IP не влияет.

b4 сообщает про `egress_ip` в списке ограничений движка всякий раз, когда у включённого маршрутизирующего сета он задан, а выбран движок TUN, независимо от режима захвата.

Та же замена - причина, по которой привязка к устройству требует второго шага. b4 восстанавливает исходный LAN-адрес из conntrack, а там, где `/proc/net/nf_conntrack` прочитать нельзя, пишет в лог, что логирование и фильтрация по устройствам будут показывать адрес аплинка, перенаправления DNS для пересылаемых клиентов выключены, а действие `reject` у блокирующего сета вырождается в тихое отбрасывание.

## Начиная с 1.80.0

Режим TUN сравнялся с путём NFQUEUE по нескольким пунктам:

- Правила маршрутизации поддерживаются и восстанавливаются так же, как их держит NFQUEUE: движок запускает routing keeper, который замечает смену адреса на выходном интерфейсе сета и перестраивает правила, когда они пропадают.
- Настройки захвата применяются при сохранении. Добавление порта в сет, изменение лимита пакетов или правка списка устройств перестраивают цепочку `B4_TUN` на месте, а не ждут перезапуска. Имя устройства, адреса и таблицы маршрутов перезапуск по-прежнему требуют.
- Маршрутизируемый трафик сохраняет свой маршрут. Переход в цепочку захвата размещается ниже цепочек маршрутизации в `PREROUTING` и `OUTPUT` и опускается вниз, если обнаружен выше них, поэтому маршрутизирующий сет успевает пометить пакет раньше, чем правило захвата заведёт его в устройство.
- Цепочки blackhole и отказа QUIC снова достижимы. Разрешения в `FORWARD`, которые ставит движок, раньше пропускали всё, что шло через устройство; теперь они ведут в `B4_TUN_FWD`, откуда для адресов из блокирующего сета выполняется возврат, и правила ниже снова срабатывают.
- Устанавливается перенаправление DNS поверх TCP. TCP-порт 53 перенаправляется в слушатель b4 и в режиме TUN, а не уходит к резолверу клиента непрочитанным.
- Masquerade больше не переписывает трафик, идущий в TUN-устройство. При включённом NAT masquerade правило теперь делает возврат для пакетов, уходящих через TUN-устройство, до правила `MASQUERADE`.
- MSS clamping, правила masquerade, sysctl для conntrack и перенаправление DNS поверх TCP переприменяются при сохранении конфигурации, а не только при старте.

## Диагностика

Всё это находится в **Настройки → Информация о системе**. Раздел **Движок** показывает устройство и его состояние, адрес и MTU, исходящий интерфейс, шлюз и определённый адрес источника, режим захвата, таблицу маршрутов, состояние правила перенаправления и цепочки захвата, применимые ограничения и счётчики пересланных пакетов, ошибок пересылки и отброшенных IPv6. Раздел **Маршрутизация** показывает вывод `ip rule` для обоих семейств, маршрут по умолчанию и содержимое таблиц захвата, обхода и таблиц отдельных сетов. Раздел **Файрвол** выводит цепочки `B4_TUN` и `B4_TUN_GATE` среди своих дампов правил. Те же данные есть в `GET /api/system/diagnostics` в полях `engine` и `routing`.

Из консоли роутера:

```sh
ip rule show
ip route show table 9999
ip route show table 9998
ip -4 route show default
iptables -t mangle -S B4_TUN
iptables -t filter -S FORWARD
iptables -t nat -S B4_TUN_SNAT
```

Что там должно быть, пока движок работает:

| Команда | Ожидается |
| --- | --- |
| `ip rule show` | Правило с приоритетом 90, отправляющее метку перенаправления в таблицу захвата (в режиме `ports`), и правило с приоритетом 100, отправляющее метку переотправки в таблицу обхода |
| `ip route show table 9999` | Маршрут по умолчанию через настоящий аплинк. По нему идут переотправленные пакеты |
| `ip route show table 9998` | Маршрут по умолчанию в TUN-устройство, в режиме `ports` |
| `ip -4 route show default` | Настоящий аплинк в режиме `ports` и TUN-устройство в режиме `default` |
| `iptables -t mangle -S B4_TUN` | Защиты по меткам, затем возвраты для маршрутизирующих сетов, затем по одному правилу перенаправления на группу портов. В режиме `default` цепочки нет |
| `iptables -t filter -S FORWARD` | Два правила для устройства, `-i` и `-o`, с переходом в `B4_TUN_FWD` |
| `iptables -t nat -S B4_TUN_SNAT` | Возврат для меток маршрутизирующих сетов, затем SNAT на адрес аплинка |

Всё это движок сверяет по таймеру и всякий раз, когда сообщение netlink говорит о смене маршрута по умолчанию, и пишет в лог, что именно восстановил. Пропавший маршрут захвата или пустая цепочка захвата также переводят состояние движка в `degraded (tun: ...)`.

Ошибки, которые называют свою причину:

- `route table N is already in use` означает, что таблицу занимает другой VPN-клиент, и в `queue.tun.route_table` нужен свободный id.
- `TUN mode needs the iptables binary` означает, что на хосте есть только `nft`, и остаётся установить `iptables-nft` или вернуть режим захвата на NFQUEUE.
