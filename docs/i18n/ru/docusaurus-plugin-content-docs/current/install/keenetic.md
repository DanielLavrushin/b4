# Keenetic

## Требования

- Роутер Keenetic с поддержкой OPKG
- Установленный Entware (обязательно)

## Установка Entware

### Новые модели (со встроенным хранилищем)

1. Открывается веб-интерфейс роутера
2. Раздел **Параметры системы**
3. Включается компонент **Менеджер пакетов OPKG**

### Старые модели (нужен USB-накопитель)

1. USB-накопитель подключается к роутеру
2. Entware устанавливается через менеджер пакетов

Подробнее: [help.keenetic.com](https://help.keenetic.com/hc/en-us/articles/360021214160)

## Компоненты Netfilter {#netfilter-components}

Прошивка Keenetic NDMS не содержит всех модулей netfilter, которые нужны b4, "из коробки". Необходимые компоненты включаются до установки b4:

1. В веб-интерфейсе роутера: **Параметры системы** → **Обновление компонентов**
2. Включается компонент **NetFilter** - это базовый компонент netfilter
3. После включения NetFilter в списке появляется **Xtables-addons for Netfilter**, его тоже нужно включить
4. Изменения применяются, далее следует перезагрузка роутера или применение компонентов

![20260423140614](../../../../../static/img/keenetic/20260423140614.png)
![20260423140726](../../../../../static/img/keenetic/20260423140726.png)

Затем по SSH устанавливается пользовательская часть iptables:

```bash
opkg install iptables
```

:::info
Компоненты системы в Keenetic доступны только под учёткой `admin`
:::

## Установка b4

По SSH на роутере:

```bash
curl -fsSL https://raw.githubusercontent.com/DanielLavrushin/b4/main/install.sh | sh
```

## Управление сервисом

```bash
/opt/etc/init.d/S99b4 start
/opt/etc/init.d/S99b4 stop
/opt/etc/init.d/S99b4 restart
```

## Пути

| Что          | Где                     |
| ------------ | ----------------------- |
| Бинарник     | `/opt/sbin/b4`          |
| Конфигурация | `/opt/etc/b4/b4.json`   |
| Сервис       | `/opt/etc/init.d/S99b4` |

## Архитектура

- Старые модели (MT7621) - `mipsle_softfloat`
- Новые модели (aarch64) - `arm64`

Установщик определяет архитектуру автоматически.

:::warning Без Entware
Без Entware b4 устанавливается в `/tmp`, который очищается при каждой перезагрузке. Для постоянной работы Entware обязателен.
:::

## Перезапись firewall {#firewall-rewrites}

NDMS перестраивает свои таблицы netfilter по собственным поводам: продление UPnP-проброса, переподключение WAN, изменение политики или компонента. При каждой перестройке пропадают цепочки, которые ей не принадлежат, в том числе цепочки b4, после чего запускаются все скрипты из `/opt/etc/ndm/netfilter.d/` с именем таблицы в `$table` и семейством в `$type`.

Установщик кладёт в этот каталог `50-b4.sh`. Скрипт посылает `SIGUSR1` запущенному процессу b4, и тот перепроверяет свои правила, как только перестройка закончится, и восстанавливает недостающие. Без хука правила всё равно вернутся при следующем опросе монитора таблиц, то есть не позже чем через `system.tables.monitor_interval` секунд (по умолчанию 10).

Правила переключателей [Доступ из интернета](../settings/security.md#expose-to-internet) стоят в таблице `filter`, которую NDMS тоже перезаписывает, и перепроверяются по тому же сигналу и с тем же интервалом. Возвращённые правила b4 пишет в лог на уровне WARN строкой `Expose: the rules opening ... were missing from ..., usually after the firewall was reloaded; restored them`, кто бы ни обнаружил пропажу, хук или опрос, поэтому эта строка появляется после перезаписи и при работающем хуке.

После перезаписи, о которой сообщил хук, в логе остаются строки `Tables rules missing after a firewall rewrite, restoring...` и `Tables rules restored successfully` уровня INFO. Та же строка уровня WARN и без слов о перезаписи означает, что опрос нашёл правила пропавшими без сигнала от хука: либо хука нет, либо правила убрал не NDMS. Ту же перепроверку можно запросить вручную:

```bash
kill -USR1 $(cat /var/run/b4.pid)
```

В режиме TUN сигнал также заставляет движок TUN сразу перепроверить цепочку захвата `B4_TUN` и переходы в неё. Восстановленную цепочку движок пишет в лог на уровне WARN строкой `TUN: capture chain B4_TUN lost N of M rules (removed outside b4) ...`, кто бы ни обнаружил пропажу, хук или опрос, а строки монитора таблиц относятся только к правилам маскарада, MSS clamp, DSCP и сетов маршрутизации. Интервал опроса в этом режиме не меньше 10 секунд.

## DNS-запросы {#dns-queries}

KeeneticOS обрабатывает таблицу raw в iptables после conntrack, и там b4 её не использует: постановка DNS-запроса в очередь в этой таблице не спасает от отбрасывания второго из двух запросов, которые устройство отправляет одновременно из одного сокета, см. примечание **Запросы и conntrack** в разделе [Что перехватывает b4](../dns.md#что-перехватывает-b4). На KeeneticOS b4 DNS-запросы не задерживает. Он снимает копию каждого запроса через NFLOG и работает с ответом резолвера, как описано в разделе [Копии запросов](../dns.md#copied-requests). При запуске в логе появляется строка:

```text
IPTABLES[iptables]: KeeneticOS runs its raw table after conntrack (kernel 4.9-ndm-5), so b4 copies DNS queries with NFLOG (group 537) instead of holding them in its queue
```

«Информация о системе» после этого показывает в разделе **Возможности ядра** строку **DNS-запросы копируются, а не задерживаются (NFLOG)** доступной. Номер группы - `queue.start_num`, по умолчанию 537.

Резолвер роутера по-прежнему получает каждый запрос и разрешает имя, в том числе имя, которое сет отправляет на DoH-резолвер, и кеширует настоящий ответ. Для имени, которое сет блокирует, закрепляет или отправляет на свой резолвер, устройство получает ответ b4 вместо ответа резолвера роутера или напрямую от b4, если ответ резолвера не пришёл за 20 мс; устройство, которое спрашивает резолвер за пределами роутера, получает ответ b4, только когда этот резолвер отвечает. Правило `nat`, которое уводит DNS на другой порт, не поддерживается. Перестройка таблиц в NDMS убирает правила копирования вместе с остальными правилами b4, и пока b4 их не восстановит, запросы проходят без копии, см. [Перезапись firewall](#firewall-rewrites).

## Диагностика

После запуска сервиса стоит проверить лог:

```bash
cat /var/log/b4/errors.log
```

Строка `xt_connbytes kernel module is not available` означает, что компоненты Netfilter включены не полностью - см. раздел [Компоненты Netfilter](#netfilter-components) выше, где активными должны быть **оба** компонента: **NetFilter** и **Xtables-addons for Netfilter**.

Строка `b4 cannot copy DNS queries with NFLOG (...)` означает, что b4 задерживает DNS-запросы в своей очереди после conntrack, и устройство, запрашивающее IPv4- и IPv6-адреса имени одновременно, часто теряет второй ответ. В скобках указана причина, например модуль `xt_NFLOG` или `nfnetlink_log`, который не загрузился. «Информация о системе» показывает в разделе **Возможности ядра** строку **DNS-запросы копируются, а не задерживаются (NFLOG)** недоступной, с недостающими модулями и строкой, которая называет компонент для включения; проверять стоит [Компоненты Netfilter](#netfilter-components) выше.

Если лог пустой (или в нём нет ошибок), веб-интерфейс b4 должен быть доступен по LAN-адресу роутера.
