DSCP rules

The fields are described under DSCP on the DNS & Routing tab, and the setup of both routers in Passing sets to another router.

A set's own DSCP value is written by the rules of Set DSCP under Settings > Core > Firewall, after the Set DSCP value, which it replaces in the packets to the set's addresses, whether Set DSCP is on or off. The rules cover forwarded traffic, b4's own connections and the fakes, fragments and segments b4 injects, in IPv4 and IPv6 whatever Enable IPv4 Support and Enable IPv6 Support say, and keep the two ECN bits. The packets Set DSCP leaves alone keep their value: loopback traffic, packets b4 sends toward LAN clients, such as DNS answers and resets, and replies within connections another host opened, such as the web interface's responses. The interface list of Set DSCP limits the sets' values too. Where the rules sit is described in Rules of the Firewall sub-tab.

Which packets get the value​

The value goes by destination address alone, whatever the protocol, the port and the set b4 picked for the connection's strategy. Port filters and TLS Version Filter do not narrow it.

AddressesWhere they come fromLifetime
StaticIP and CIDR targets, GeoIP categories and ASNsWhile the set lists them
Learned from DNSAnswers for the set's domains over UDP and TCP: forwarded, pinned or from the set's DNS redirectResolved IP TTL (seconds) while routing is on, otherwise 1 hour

b4's own lookupsThe first 256 domain entries that are not regexp:, GeoSite excluded, when the set starts writing its value or its domains or resolver change, then every half lifetime, at least 5 minutes apartAs for DNS

A learned address seen again gets a fresh lifetime once less than half of it is left, or at once when b4's lookup finds it. IP Version Filter at 4 or 6 leaves out the other family. Domain-only matching turns learning off.

Where sets overlap, an address learned for a set wins over every static range; among static ranges the longest prefix wins; with the same prefix or learned address, the set higher in the list wins. Only sets whose value is applied take part.

The router's own connections, the connections b4's SOCKS5 proxy opens directly, and the fakes and segments b4 injects get the value by destination as well, whatever Router's own traffic says. Queries to a set's resolver carry a value only when some set lists the resolver's address, and then all of them do, the devices' included.

The first connection​

A packet to an address not yet written for the set leaves without the value. Static targets are written when the configuration is applied. After a forwarded or pinned answer over UDP, the NFQUEUE engine holds the answer until the address is written, at most 250 ms, and the TUN engine does not hold it. An answer from the set's DNS redirect, and any answer over TCP, goes out after the address is written. A connection whose address comes from its own ClientHello or QUIC Initial starts without the value, and b4's own lookups help only when the device got the same address. Where the devices' DNS does not pass through b4, as with b4 as a container on MikroTik or with devices on DoH, DoT or DoQ, IP, CIDR, GeoIP and ASN targets give the value from the first packet.

Routing mode and scope​

The Per-set DSCP group of System Info names a refused set's reason with these codes:

SetReason
Upstream SOCKS5 proxy mode: the traffic leaves as b4's own connections to the proxyrouting_proxy
Telegram over WebSocket (built-in) mode: shared WebSocket connectionsrouting_mtproto_ws
Block (blackhole) mode: the packets never leaverouting_block
Source devices listed, included or excluded: the stage that writes the value cannot see the devicesource_devices
Routing limited to Source Interfaces: that stage cannot see the arriving interfacesource_interfaces
Device Filtering with a device selected, for every setdevice_filter
No domain, IP, GeoIP or ASN target, or Domain-only matching without IP, GeoIP or ASN targetsno_addresses

In Network interface mode the value is written into the packets that leave through an interface the list covers. Through a tunnel, the router in front sees only the tunnel's packets, and WireGuard writes 0 into their DSCP field. With Skip IPTables/NFTables Setup on, no set writes its value.

Firewall rules and cost​

The sets' rules sit after the Set DSCP rule, in its chain B4_DSCP with iptables or its table inet b4_dscp with nftables, installed while Set DSCP is on or an enabled set writes its own value.

BackendWhat the sets addNeeds
iptablesA rule that ends the chain for a packet to none of the sets' addresses, then one rule per value and per set that learns addresses. The ipsets b4d_u_v4, b4d_ul_v4, b4d_s<value>_v4, b4d_l_<set>_v4 and their _v6 pairs hold the addressesipset and the xt_set kernel module. Without them b4 logs a warning, and that family gets only the Set DSCP value
nftablesThe maps s4_<n> and s6_<n>, a chain v<value> per value, and the sets l_<set>_4 and l_<set>_6 of learned addressesNothing beyond Set DSCP

<set> is derived from the set's id; Checking marks on the router lists them. Every packet the host sends, apart from those left alone at the top of the chain, costs extra lookups: with nftables one in the static map and one per learning set; with iptables up to two in b4d_u_* and b4d_ul_*, then one per value and per learning set for a packet to a set's address.

System Info lists a Per-set DSCP group under Firewall while an enabled set has its own value switched on: a line per set, a line per iptables binary that cannot use ipsets, and the backend.
